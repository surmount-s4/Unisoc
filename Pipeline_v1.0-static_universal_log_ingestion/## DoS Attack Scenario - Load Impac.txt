## DoS Attack Scenario - Load Impact Analysis

Let me analyze what happens to your correlation engine when a **DoS (Denial of Service) attack** generates massive log volumes:

---

### 🚨 **Critical Failure Points During DoS**

#### **1. CSV Data Explosion**
```
Normal Load: 250 events/min × 100 endpoints = 25,000 events/min
DoS Attack:  10,000 events/min × 100 endpoints = 1,000,000 events/min

CSV File Growth:
- Normal: ~20 MB/hour
- DoS: ~800 MB/hour to 2+ GB/hour
```

**Impact on your code:**
- `load_and_filter_csv()` will load **entire CSV into memory** (pandas DataFrame)
- 2 GB CSV = ~4-8 GB RAM usage after DataFrame overhead
- **System crashes** when CSV > available RAM

---

#### **2. Process Chain Hash Table Overflow**

From your `extract_process_chains()` method:

```python
hash_table_creation = {}  # Stores ALL process relationships
hash_table_source_target = {}  # Stores ALL network connections
```

**During DoS:**
- Each event creates hash table entries
- DoS events (EventID 3 - Network) create **source-target pairs**
- Network scan DoS: 1000s of unique target IPs
- **Hash table grows to 100K-1M+ entries**

**Memory consumption:**
```
Normal: ~5,000 processes × 2 KB = 10 MB
DoS: ~500,000 processes × 2 KB = 1 GB (hash table alone!)
```

---

#### **3. Time Window Catastrophe**

Your `_create_time_windows()` with 5-second windows:

```python
WINDOW_SECONDS = 5  # 5-second windows

# During DoS attack:
Events per 5-sec window: 1,000,000 events/min ÷ 12 = 83,333 events/window
```

**What happens:**
1. **Each window** contains 50K-100K events
2. **LLM inference** for 100K events = **massive prompt** (>500 KB text)
3. **Ollama timeout** (120 seconds) will **definitely trigger**
4. **Queue backlog** grows exponentially

**Result:** 
- Windows pile up faster than LLM can process
- System enters **infinite backlog mode**

### 📊 **Real-World DoS Scenario**

**Attack Type:** SYN Flood DoS
```
Target: Web server
Attack rate: 100,000 packets/second
Log generation: EventID 3 (Network Connection)

Per-endpoint impact:
- 100K events/sec × 60 sec = 6 million events/min
- CSV growth: 6 MB/min = 360 MB/hour
- Hash table: 6M entries × 2 KB = 12 GB RAM
```

**Your pipeline behavior:**
1. **T+0 min:** DoS starts, CSV begins growing
2. **T+5 min:** First window processes → LLM timeout (too many events)
3. **T+10 min:** CSV reaches 60 MB, DataFrame load slows
4. **T+15 min:** Hash table hits 3 GB RAM, system swaps
5. **T+20 min:** LLM queue backlog = 200+ windows
6. **T+30 min:** System crashes (OOM) or hangs indefinitely

---

### 💡 **Why Current Architecture Fails**

1. **No Event Rate Limiting**
   - Accepts unlimited events per window
   - No throttling or sampling

2. **No Memory Protection**
   - CSV loads entirely into RAM
   - Hash tables grow unbounded
   - No garbage collection triggers

3. **No LLM Batch Size Control**
   - Sends all window events to LLM
   - No chunking or summarization
   - No prompt size validation

4. **Sequential Processing**
   - One window at a time
   - Can't parallelize to catch up
   - Backlog accumulates linearly

5. **No Attack Detection**
   - Doesn't distinguish DoS from normal activity
   - Treats 100K events same as 10 events
   - No adaptive behavior

---

### 🔧 **Required Mitigations** (We can implement these)

#### **Immediate Fixes:**

1. **Event Sampling** (above threshold)
2. **Window Event Cap** (max 1000 events/window)
3. **CSV Chunking** (stream, don't load all)
4. **Memory Monitors** (kill if > 80% RAM)
5. **LLM Prompt Size Validation** (reject if > 100 KB)

#### **Architecture Changes:**

1. **Pre-filtering** (drop obvious DoS noise)
2. **Event Deduplication** (hash-based)
3. **Tiered Processing** (fast path for anomalies)
4. **Rate Limiting** (per-endpoint quotas)
5. **Circuit Breaker** (auto-disable during floods)

---
